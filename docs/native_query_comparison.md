## 查询与文件如何比较

实际 GOC2 文件包含 16 B 公共头、Float64 XYZ、每面片 12 B 类型／阶数／节点数头和 Uint32 索引。两种方法都共享重复节点。n 条面带的控制点为 4n+2；覆盖相同分区的 2n 个完整 P₃ 三角面的共享节点为 12n+4。没有用复制节点抬高三角基线成本。稀疏系数或全局公式编码可能更小，本结果只涉及明确的通用节点表示，并非信息论最优。

双方先验证模型，预计算多项式系数；≤8 个面片用扫描，更多时均使用同样的 32×32 包围盒索引。计时操作为点定位、高程、笛卡尔解析梯度和被消费的累加校验和；不包含读取、解码或预计算。固定 128×32 个内部坐标覆盖最多 128 条面带，五批预热后进行 17 轮 AB/BA 交替计时。每组采用共同批次数，旧实现另校准批次数并测五轮，仅供回归参考。

环境：Intel Core i7-14650HX，Windows x64，Node v24.13.0，V8 13.6.233.17-node.37。p10–p90 为观测分位数，不能当置信区间或跨设备保证；单轮不一定更快。准备耗时仅单次记录，不用于延迟优势结论。执行缓存不算作新的存档编码，文件大小不等于运行内存；这些 CPU 数值不等于 ArcGIS 软件耗时或浏览器/GPU 帧率。

## 实现与复核

- `data-pipeline/piecewise_ruled_control.py`：固定 8 / 32 / 128 档源函数、共享节点、全域求积与完整文件。
- `frontend/src/compare/preparedOrderQuery.ts`：两类函数的预计算、同策略空间索引及直接高程／梯度查询。
- `frontend/scripts/benchmark-order-query.mjs`：固定查询、正确性门槛、交替计时及全部原始记录。
- `data-pipeline/publish_native_query_performance.py`：重新构建分段模型，核验全域精度、全部 220 条记录、分位数、校验和、源代码哈希及文件，生成不可覆盖证据包。
- `frontend/public/research/native-query-v1/`：完整 JSON / GOC2、固定坐标、原始 CSV、科学图、实现源文件和 ZIP。

复现时使用新的私有目录，避免覆盖历史证据：

```powershell
.venv/Scripts/python.exe data-pipeline/piecewise_ruled_control.py --output .local/research/my-piecewise-run
node frontend/scripts/benchmark-order-query.mjs .local/research/my-query-run .local/research/my-piecewise-run
```

正式城市档案保持原有格式；本研究编码供可复核的结构实验使用。原严格凸曲面的 P₂ 控制仍完整保留：27/27 档 P₂ 全域误差更低。因此“98.3% 误差降低”仍明确限定为对论文 P₁ 复现基线，不推广为优于所有高阶方法。

验收：763 项前端测试、4 项新增研究核验和生产构建通过；浏览器实际操作了规模切换、滑块查询、二次／三次函数剖面、全表展开和 ZIP 下载。双方高程和梯度显示一致，图片正常，未出现新的控制台错误。下载 ZIP 与发布 SHA-256 完全一致，旧正式城市及冻结研究数据未改动。
